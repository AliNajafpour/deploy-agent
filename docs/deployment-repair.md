# اصلاح خطای بک‌اند و موانع انتشار

این مسیر خطای مستند در کد موجود بک‌اند، مانند HTTP 500 در یک handler تو‌در‌تو،
و مشکلات لازم برای ساخت و شروع برنامه را پوشش می‌دهد: manifest ناقص، فرمان شروع،
پورت و bind، خطای نحو یا وابستگی جاافتاده. اصلاح باید رفتار مورد انتظار و حالت‌های
موفق برنامه را حفظ کند. طراحی صفحه، قابلیت نامرتبط، تغییر schema، مهاجرت داده و
تضعیف احراز هویت، مجوز دسترسی یا اعتبارسنجی ورودی در این محدوده نیست.

## مسیر اجرا

1. در رابط «رفع مانع انتشار» را انتخاب کنید، یا پس از تشخیص/انتشار ناموفق دکمهٔ
   «بررسی و اصلاح مانع انتشار» را بزنید. API همان RunRequest با intent=repair را می‌پذیرد.
2. هسته شواهد را جمع می‌کند و از سورس یک بستهٔ ثابت می‌سازد. فایل‌های متنی مجاز
   همراه هش قبل، با حذف فایل حاوی نشانهٔ مقدار محرمانه، به planner داده می‌شوند.
   در درخواست اصلاح، مسیرهای اشاره‌شده در لاگ فقط برای اولویت‌بندی فایل‌های داخل
   همان بسته استفاده می‌شوند؛ هیچ مسیر میزبان از روی متن لاگ خوانده نمی‌شود.
3. مدل یک repair_deploy شامل متن کامل فایل‌های اصلاحی پیشنهاد می‌دهد. هسته مسیر،
   هش قبل، اندازه، تکراری‌نبودن، نبود مقدار محرمانه و نوع درخواست را بررسی می‌کند.
4. فایل‌ها در پوشهٔ موقت جدا اصلاح می‌شوند. JSON/TOML و نحو Python یا Node بررسی
   می‌شوند. کد برنامه، importها، اسکریپت npm و نصب پکیج روی میزبان اجرا نمی‌شوند.
5. diff، هش بسته و نتایج بررسی پیش از تأیید نمایش داده می‌شوند. همان بستهٔ ثابت
   پس از تأیید آپلود می‌شود؛ وضعیت release و سلامت HTTP جدا بررسی می‌شوند.

پیشنهاد یا رد طرح هیچ تغییر ابری ایجاد نمی‌کند. تأیید همان قواعد digest، ثبت
اقدام و ادامه پس از restart هسته را دارد. انتشار نسخهٔ بعدی از سورس اصلی، خودبه‌خود
این اصلاح را ندارد؛ بسته و diff اصلاح‌شده در گزارش همین عملیات ثبت می‌شوند.

## محدوده و محدودیت‌ها

فایل‌های شناخته‌شدهٔ استقرار و شروع مانند package.json، requirements.txt،
pyproject.toml، liara.json، Dockerfile، Procfile و app/main/server entrypointها
در ریشه یا پوشهٔ backend/server مجازند. در درخواست اصلاح، فایل‌های Python موجود
در پکیج‌های تو‌در‌تو و JavaScript موجود در backend/server/api یا src/backend،
src/server و src/api نیز با هش دقیق قابل اصلاح‌اند. افزودن فایل دلخواه بک‌اند مجاز
نیست؛ فایل جدید فقط از فهرست قبلی فایل‌های استقرار و شروع پذیرفته می‌شود.
فایل‌های frontend، UI، tests، migrations، کلیدها و مسیرهای بیرون پروژه مجاز نیستند.
JavaScript در src عمومی مجاز نیست چون ممکن است UI باشد. حداکثر ۸ فایل اصلاحی،
هر فایل ۲۴ هزار بایت و در مجموع ۶۰ هزار بایت. همین سقف مجموع برای متن ورودی مدل
اعمال می‌شود؛ manifestها، فایل اشاره‌شده در traceback و سپس entrypointها اولویت دارند.

وجود نام فایل در این فهرست، درستی معنایی پیشنهاد مدل یا امن‌بودن تغییر منطق را ثابت نمی‌کند؛ diff باید
بازبینی شود. بررسی ساختاری جای تست برنامه و بررسی سلامت پس از ساخت را نمی‌گیرد.
نیاز به فایل خارج از این محدوده، اطلاعات محرمانه یا انتخاب نسخهٔ نامشخص باید به
سؤال یا محدودیت روشن برسد. فایل نادیده‌گرفته‌شده توسط ignore بی‌صدا منتشر نمی‌شود.

افزودن وابستگی در manifest بدون lock پشتیبانی می‌شود. تغییر وابستگی با lockfile
موجود خودکار انجام نمی‌شود؛ سازگاری اعلام نسخه در ریشهٔ lock به‌تنهایی کافی نیست.
نصب پکیج و وابستگی‌های سیستم در محیط builder و بر پایهٔ فایل تأییدشده انجام می‌شود.
نسخهٔ پکیج یا نگاشت نام import به نام توزیع نباید بدون شواهد حدس زده شود.

## بازتولید

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_repair -v
.\.venv\Scripts\python.exe -m unittest tests.test_backend_repair -v
.\.venv\Scripts\python.exe -m tests.repair_agent --provider scripted
.\.venv\Scripts\python.exe -m tests.repair_agent --provider codex --report .lyara/checks/repair-codex.json
.\.venv\Scripts\python.exe -m tests.repair_agent --provider codex --serve --port 8796
```

سه پروژهٔ افزوده در tests/repair_projects هستند: فرمان شروع Node اشتباه،
وابستگی Python جاافتاده و پورت بک‌اند اشتباه. builder آزمایشی فقط تغییرات مشخص
همین fixtureها را پس از بررسی کامل بسته اجرا می‌کند. نصب Python در venv موقت،
با colorama 0.4.6 از wheelhouse محلی یا کش موجود uv و بدون دانلود شبکه انجام می‌شود.
مسیر wheelhouse با LYARA_WHEELHOUSE قابل تعیین است؛ نبودن بسته در هر دو منبع خطای روشن می‌دهد.
API ابر شبیه‌سازی می‌شود؛ مدل در حالت codex، نصب، فرایند و HTTP واقعی‌اند.
آزمون حساب زندهٔ لیارا طبق تصمیم کاربر خارج از محدوده است.

آزمون test_backend_repair یک route آزمایشی ثابت را با فهرست خالی اجرا می‌کند و
HTTP 500 را بازتولید می‌کند، سپس اصلاح همان فایل تو‌در‌تو را با طرح صریح بررسی می‌کند.
تست، نسخهٔ قبل و بعد از fixture ثابت را اجرا می‌کند؛ هسته فقط نحو بستهٔ پیشنهادی
را بررسی می‌کند و کد آپلودشده را اجرا نمی‌کند. رد طرح، هش فایل موجود، محرمانگی،
مسیرهای ممنوع و تطابق بایت‌های آپلود با بستهٔ تأییدشده نیز بررسی می‌شوند.

برای استفادهٔ داخلی، deployment_files(artifact, secrets=(), include_backend=False,
observations=None) رفتار قبلی را به‌صورت پیش‌فرض حفظ می‌کند. درخواست repair و ابزار
بازرسی بک‌اند باید include_backend=True بدهند و شواهد موجود را در observations
بفرستند. validate_edits فقط فایل‌های موجود در همین context و هش آن‌ها را برای
اصلاح کد تو‌در‌تو می‌پذیرد؛ فایل بزرگ، محرمانه یا حذف‌شده قابل بازنویسی نیست.
