# میزبانی خود Lyara روی لیارا

تاریخ بررسی: ۲۰۲۶-۱۰-۲۳. منابع این یادداشت فقط مستندات رسمی لیارا و مخزن رسمی CLI هستند. هیچ حساب واقعی، کلید، خرید یا استقراری در این بررسی استفاده نشده است. تنظیمات اختصاصی Lyara از کد همین مخزن خوانده شده‌اند؛ پیشنهادهای اجرایی از قابلیت‌های مستند پلتفرم جدا شده‌اند.

## مسیر عملی

خود دستیار یک برنامهٔ مستقل Docker باشد. پس از بالا آمدن، پروژه‌های کاربران را با API لیارا منتشر می‌کند. برای میزبانی دستیار نیازی به اجرای Docker daemon یا Liara CLI داخل کانتینر نیست؛ آداپتر فعلی `lyara/liara.py` مستقیماً HTTPS API را فراخوانی می‌کند. فرمان اجرای وب فعلی:

```text
python -m lyara serve --host 0.0.0.0 --port 8080
```

فایل‌های `Dockerfile`، `.dockerignore`، `.liaraignore` و `liara.json` اکنون در ریشهٔ مخزن آماده‌اند. Dockerfile شامل Python و Node برای بررسی نحو اصلاحات است؛ اجرای پیش‌فرض یک پردازش وب با مدل API است. Docker روی سیستم بررسی نصب نیست، بنابراین ساخت image و استقرار زنده هنوز تأیید نشده‌اند.

مسیر پیشنهادی برای همین مخزن، اتصال گیت‌هاب است: پس از انجام گام‌های ساخت برنامه، دیسک و متغیرها، در «استقرار جدید ← گیت‌هاب»، مخزن `AliNajafpour/deploy-agent` و شاخهٔ `main` را انتخاب و یک‌بار استقرار دستی را اجرا کنید. فایل آمادهٔ `liara.json` فقط پورت و دیسک را مشخص می‌کند و فیلدهای `app` و `platform` ندارد؛ این با مسیر GitHub مستندات سازگار است. [اتصال GitHub](https://docs.liara.ir/paas/docker/how-tos/deploy-app/)

۱. در کنسول لیارا، حساب شخصی یا تیم موردنظر را انتخاب کنید و یک برنامه با پلتفرم **Docker**، شناسهٔ یکتا و شبکهٔ خصوصی بسازید. انتخاب منابع و بستهٔ امکانات بخشی از ساخت برنامه است. [ساخت برنامهٔ Docker](https://docs.liara.ir/paas/docker/how-tos/create-app/)

۲. در بخش «دیسک‌ها»ی همان برنامه، دیسکی با نام `data` و اندازهٔ متناسب با فایل‌های پروژه‌ها بسازید. اندازه برحسب GB است؛ ساخت دیسک و اتصال آن دو مرحلهٔ جدا هستند. [ساخت دیسک](https://docs.liara.ir/paas/disks/create/)

۳. تصویر Docker باید Python، وابستگی‌های `pyproject.toml` و فایل‌های بستهٔ Lyara را نصب کند و فرمان بالا را اجرا کند. لیارا Dockerfile را build می‌کند؛ پورت ثبت‌شده باید پورت واقعی سرور باشد. نمونهٔ حداقلی **برای استقرار با CLI**:

```json
{
  "app": "YOUR_LYARA_APP_ID",
  "platform": "docker",
  "port": 8080,
  "disks": [{"name": "data", "mountTo": "/data"}]
}
```

`platform` و `port` طبق [راهنمای استقرار Docker](https://docs.liara.ir/paas/docker/how-tos/deploy-app/) هستند. کلید اتصال دقیقاً `mountTo` است؛ `mountPath` صحیح نیست. دیسک باید از قبل موجود باشد. مسیر Docker را مطلق بنویسید و دیسک را به `/` وصل نکنید. [تعریف مسیر دیسک](https://docs.liara.ir/paas/disks/route/)، [دیسک در Docker](https://docs.liara.ir/paas/docker/how-tos/use-disk/)

۴. در کنسول برنامه، «تنظیمات ← متغیرها»، مقادیر زیر را ثبت کنید. کنسول از ورود مستقیم، copy/paste و آپلود فایل env پشتیبانی می‌کند. کلیدها را در Dockerfile، `liara.json` یا سورس قرار ندهید. [تنظیم متغیرهای محیطی](https://docs.liara.ir/paas/details/envs/)

| متغیر Lyara | مقدار / کاربرد |
| --- | --- |
| `LYARA_PROVIDER` | `api` |
| `LYARA_LLM_BASE_URL` | `https://ai.boxapi.ir/ai/v1`؛ پیش‌فرض فعلی پروژه |
| `LYARA_MODEL` | `openai/gpt-6-luna`؛ پیش‌فرض فعلی پروژه |
| `LYARA_LLM_API_KEY` | کلید واقعی BoxAPI؛ دسترسی و مدل باید جداگانه در حساب فراهم باشند |
| `LIARA_API_TOKEN` | کلید API حسابی که سایت‌ها را منتشر می‌کند |
| `LIARA_TEAM_ID` | شناسهٔ تیم هدف؛ برای حساب شخصی خالی |
| `LYARA_ACCESS_TOKEN` | مقدار تصادفی قوی برای ورود به وب دستیار؛ اجرای غیرمحلی بدون آن رد می‌شود |
| `LYARA_PUBLIC_HOST` | فقط hostname، مثلاً `YOUR_LYARA_APP_ID.liara.run`؛ بدون `https://` یا مسیر |
| `LYARA_WORKSPACE` | `/workspace`؛ پوشهٔ خالی مستقل از کد خود دستیار، پیش‌فرض Dockerfile |
| `LYARA_DATA_DIR` | `/data`؛ محل پایدار وضعیت خصوصی و فایل‌های آپلودشده، پیش‌فرض Dockerfile |
| `LYARA_HOSTING_OPTIONS` | برای ساخت سایت جدید لازم است؛ گزینه‌های واقعی پلن با شناسه و هزینهٔ بررسی‌شده توسط اپراتور |

در قالب آماده، ZIPهای کاربران زیر `/data/uploads` و تمام SQLiteها و `inputs.key` زیر `/data` می‌مانند؛ `/workspace` ورودی ZIP نیست و فایل کاربر در آن نگهداری نمی‌شود. اگر بعداً سورس محلی برای CLI قرار می‌دهید، workspace را روی مسیر پایدار مجزا مثل `/data/projects` تنظیم و آن پوشه را ایجاد کنید. این چیدمان پیشنهاد این پروژه است، نه ساختار اجباری لیارا. متغیرهای BoxAPI از `.env.example` و `lyara/providers.py` این مخزن‌اند؛ این تحقیق اعتبار کلید یا دسترسی زندهٔ مدل را آزمایش نکرده است.

فایل `.env` توسعه را همراه سورس منتشر نکنید؛ به‌خصوص مقادیر محلی `LYARA_DATA_DIR=.lyara` و `LYARA_WORKSPACE=.` را در پنل کپی نکنید. کلیدهای خود دستیار در پنل لیارا تنظیم می‌شوند؛ اطلاعات دیتابیس و سرویس‌های هر سایت از فرم همان سایت در رابط دستیار دریافت می‌شوند.

برای گزینه‌های میزبانی، شناسهٔ واقعی را با `liara plan:list` بگیرید و قیمت و شرایط فعلی را در پنل بررسی کنید. یک نمونهٔ ساختار، با مقدارهایی که اپراتور باید جایگزین کند:

```dotenv
LYARA_HOSTING_OPTIONS=[{"id":"REAL_PLAN_ID","title":"سایت کوچک","cost":"قیمت و شرایط واقعی همین پلن"}]
```

فهرست خالی، اجازهٔ ساخت برنامهٔ جدید نمی‌دهد؛ سایت موجود با پلن فعلی جداست. [مشاهدهٔ پلن‌ها](https://docs.liara.ir/references/cli/see-platform-plans/)

۵. روی سیستم توسعه، CLI رسمی را نصب کنید، وارد حساب شوید و از ریشهٔ پروژه استقرار را انجام دهید:

```text
npm install -g @liara/cli
liara login
liara deploy --app YOUR_LYARA_APP_ID --platform docker
```

این روش جایگزین GitHub است و با فایل آمادهٔ مخزن، نام و پلتفرم را از آرگومان فرمان می‌گیرد. برای تیم، `--team-id=YOUR_TEAM_ID` را به همان فرمان اضافه کنید. CLI گزینهٔ `--api-token` هم دارد، اما ورود تعاملی از درج کلید در فرمان بی‌نیازتان می‌کند. [استقرار با CLI](https://docs.liara.ir/references/cli/deploy-app/)، [مرجع رسمی CLI](https://github.com/liara-cloud/cli/blob/master/README.md)

۶. آدرس `https://YOUR_LYARA_APP_ID.liara.run` را باز کنید، با توکن دستیار وارد شوید و ابتدا یک پروژهٔ آزمایشی را با تأیید صریح طرح منتشر کنید. این زیردامنه پس از ساخت برنامه اختصاص می‌یابد. [زیردامنهٔ پیش‌فرض](https://docs.liara.ir/paas/domains/default-subdomain/)

## نکات عملی که جلوی از دست رفتن وضعیت را می‌گیرند

- فایل‌سیستم Docker در لیارا به‌طور پیش‌فرض writable است ولی تغییرات آن با ری‌استارت از بین می‌روند. اعلام `VOLUME` داخل Dockerfile جای ساخت و mount دیسک لیارا را نمی‌گیرد. [دیسک در Docker](https://docs.liara.ir/paas/docker/how-tos/use-disk/)
- تمام `LYARA_DATA_DIR` باید پایدار بماند: SQLiteهای وضعیت و ورودی‌ها، checkpointها، فایل‌های مرتبط و کلید `inputs.key`. در کد فعلی، `inputs.sqlite` بدون همان کلید Fernet قابل استفاده نیست. هنگام جابه‌جایی داده، کل پوشهٔ وضعیت را یکجا و محرمانه منتقل کنید. این الزام از `lyara/inputs.py` و `lyara/runtime.py` است.
- برای نسخهٔ فعلی Lyara، یک پردازش و یک نمونهٔ فعال نگه دارید؛ وضعیت و قفل‌های درون‌پردازشی برای اجرای همزمان چند نمونه طراحی نشده‌اند. این یک محدودیت طراحی Lyara است؛ در صفحات رسمی بررسی‌شده حکمی عمومی مبنی بر «هر برنامهٔ دارای دیسک در لیارا حتماً فقط یک replica دارد» پیدا نشد.
- پیشنهاد این پروژه: قابلیت استقرار بدون اختلال را برای این نسخهٔ دارای SQLite و اجرای عملیات درون‌پردازشی خاموش کنید تا دو نسخه در دورهٔ انتقال همزمان کار نکنند. مستندات می‌گویند rollout بدون اختلال نسخهٔ جدید را در پس‌زمینه اجرا و سپس ترافیک را منتقل می‌کند؛ امکان خاموش کردن آن در تنظیمات هست. [استقرار بدون اختلال](https://docs.liara.ir/paas/details/zero-downtime-deployment/)
- گزینهٔ اتصال مستقیم GitHub با نمونهٔ CLI فرق دارد: مستندات Docker برای مسیر GitHub حذف فیلدهای `app` و `platform` را درخواست می‌کند. نمونهٔ این یادداشت مخصوص CLI است. [مسیرهای استقرار Docker](https://docs.liara.ir/paas/docker/how-tos/deploy-app/)

## حدود واقعی قابلیت فعلی

پس از بالا آمدن، کاربر ZIP سایت را می‌فرستد، دستیار فایل‌ها و شواهد را بررسی می‌کند، اطلاعات ضروریِ کم‌شده را از فرم می‌گیرد و بعد از تأیید طرح، API لیارا را برای انتشار فراخوانی می‌کند. Docker daemon یا اجرای کد سایت داخل کانتینر دستیار لازم نیست؛ build سایت‌ها در زیرساخت لیارا انجام می‌شود.

مسیر `repair_deploy` می‌تواند manifest وابستگی، فرمان شروع و باگ در فایل‌های موجود بک‌اند را اصلاح کند. فایل‌های مرتبط با traceback اولویت دارند؛ بستهٔ اصلاحی با diff، بررسی نحو و تأیید دوباره منتشر می‌شود. تغییر رابط، افزودن قابلیت، migration و تضعیف احراز هویت مجاز نیست. کد آپلودشده روی میزبان دستیار اجرا نمی‌شود؛ build و اجرای سایت به محیط استقرار تعلق دارد. حدود مسیر در [راهنمای اصلاح](deployment-repair.md) آمده است. پایش ماندگار نیز اختیاری است و پس از دو شکست متوالی، فقط تحلیل و پیشنهاد قابل تأیید می‌سازد.

این نسخه یک اپراتور و یک حساب/تیم میزبانی پیکربندی‌شده دارد. ورود و جداسازی حساب مستقل برای هر کاربر عمومی پیاده‌سازی نشده است. MCP موجود از نوع stdio برای اتصال به کلاینت کدنویسی است؛ API وبِ دستیار، endpoint راه‌دور MCP محسوب نمی‌شود.

## کلیدها، تیم و محدودیت‌های مستند

کلید API لیارا در منوی API کنسول با مدت اعتبار انتخابی ساخته می‌شود. احراز هویت `Authorization: Bearer …` است. درخواست تیم باید `teamID` داشته باشد؛ آداپتر همین پروژه آن را در query می‌فرستد. `LIARA_API_TOKEN` اختیار انتشار سایت‌هاست، درحالی‌که `LYARA_ACCESS_TOKEN` ورود به خود دستیار را کنترل می‌کند؛ این دو باید مقادیر مستقل داشته باشند. [مرجع API و تیم](https://docs.liara.ir/references/api/about/)

طبق جدول فعلی بسته‌های امکانات، سقف **آپلود سورس استقرار** در برنزی/نقره‌ای/طلایی به‌ترتیب ۱۲۸/۲۵۶/۲۵۶ مگابایت، سقف build برابر ۵/۱۰/۲۰ دقیقه و تعداد استقرار روزانه ۲۰/۵۰/نامحدود است. جدول همچنین برنزی را بدون پشتیبان‌گیری و نقره‌ای/طلایی را دارای گزینه‌های پشتیبان‌گیری نشان می‌دهد. این اعداد مربوط به انتشار سورس در لیارا هستند؛ سقف آپلود ZIP توسط کاربر به وب Lyara محسوب نمی‌شوند. [جدول بسته‌های امکانات](https://docs.liara.ir/paas/details/plans/software-plans/)

درخواست عمومی از reverse proxy لیارا عبور می‌کند. صفحهٔ رسمی بررسی‌شده برای حداکثر بدنهٔ HTTP، timeout درخواست، رفتار streaming یا headerهای forwarded مقدار عددی یا قرارداد مشخصی نمی‌دهد. بنابراین نباید از سقف سورس استقرار، سقف ZIP وب دستیار یا زمان مجاز پاسخ LLM را نتیجه گرفت؛ این موارد در استقرار واقعی باید با تنظیمات جاری و پشتیبانی لیارا مشخص شوند. [پروکسی معکوس](https://docs.liara.ir/paas/details/reverse-proxy/)

انتخاب RAM پیشنهاد قطعی این تحقیق نیست؛ منابع باید با مصرف واقعی Lyara سنجیده شوند. مستندات پلن سخت‌افزاری و بستهٔ امکانات را جدا تعریف می‌کند؛ قیمت یا شناسهٔ پلن را از نام‌هایی مثل «زمین» حدس نزنید. [پلن‌های سخت‌افزاری](https://docs.liara.ir/paas/details/plans/hardware-plans/)
