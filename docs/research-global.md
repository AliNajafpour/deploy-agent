# Comparable deployment and SRE assistants

Research date: 2026-10-23. Sources are official documentation, first-party engineering posts and project source repositories. This is a design comparison, not a hands-on product benchmark. Availability and safety settings vary by version and account.

Lyara should copy the operational discipline of these projects: inspect real state, cite evidence, propose a specific change, obtain approval, execute through a narrow API, and verify the result. It also needs a complete first-deployment path. An incident investigation alone does not meet the challenge in `challange.md`.

## Comparison

| Product or project | Verified capability | Useful pattern for Lyara | Boundary or cost of copying |
| --- | --- | --- | --- |
| AWS DevOps Agent | Current directed-action documentation supports investigation followed by explicitly approved mutations. Approval identifies the operation and parameters; execution credentials cover the approved resource and a bounded time window. [Directed actions](https://docs.aws.amazon.com/devopsagent/latest/userguide/working-with-devops-agent-working-with-directed-actions.html) | Bind approval to a concrete operation and immutable parameters. Show risk, expected effect and recovery steps. | AWS IAM session policies have no demonstrated Liara equivalent. Enforce the narrower action contract in Lyara itself. |
| Azure SRE Agent | Review mode proposes Azure infrastructure writes for approval. Its documented mitigation sequence includes diagnosis, permission checks, execution and verification, with an audit record. [Mitigations](https://sre.azure.com/docs/capabilities/execute-mitigations), [run modes](https://learn.microsoft.com/en-us/azure/sre-agent/agent-run-modes) | Distinguish permission to access a resource from approval to change it. Show the result of the post-action check. | Review mode's documented approval boundary covers Azure infrastructure operations; other tool actions need separate governance. |
| incident.io Investigations | The engineering team describes findings as evidence-backed records that can change or be discounted when new evidence contradicts them. Investigations uses telemetry, deployment changes, incident history, documentation and code. [Engineering account](https://incident.io/blog/building-investigations-what-it-takes-to-build-an-ai-sre) | Give findings stable IDs and cited observations. Preserve a contradicted finding as refuted rather than silently replacing the story. | Its production context and incident integrations exceed this MVP. A small evidence list is sufficient now. |
| Rootly AI SRE | Investigations tests competing explanations and can report a confirmed cause, contributing factor, inconclusive result or missing-access blockage. Memory notes are leads to check, not evidence. [Overview](https://docs.rootly.com/ai/ai-sre/overview), [result interpretation](https://docs.rootly.com/ai/ai-sre/reading-the-result) | Separate observed facts, suspected causes and missing data. Allow an honest inconclusive answer with a useful next check. | Some tools can change state without confirmation. Read-only provider identities and selected tool permissions remain necessary. |
| HolmesGPT | The open-source project provides an SRE investigation agent. Runbooks gather data step by step through CLI, HTTP and Python interfaces. Its operator can verify rollouts and gate pipelines on health checks. [Source](https://github.com/HolmesGPT/holmesgpt), [runbooks](https://holmesgpt.dev/0.23.0/reference/runbooks/), [deployment verification](https://holmesgpt.dev/latest/operator/deployment-verification/) | Use a few deterministic investigation checklists and make deployment verification an explicit stage. | Kubernetes CRDs and a general shell tool would add complexity. Use documented Liara endpoints and bounded HTTP checks instead. |
| kagent | Its agent configuration separates model providers from agents. Tool bindings can require human approval. The docs describe concrete differences between kagent, Codex and Claude execution backends. [Providers](https://kagent.dev/docs/kagent/1.x/setup/model-providers/about-model-providers/), [human approval](https://kagent.dev/docs/kagent/1.x/agents/human-in-the-loop/) | Keep one planning schema across API, Codex CLI and Claude Code. Reject unsupported backend capabilities explicitly. | Similar tool names do not imply equivalent approval behavior. Kubernetes infrastructure is unnecessary for this local service. |
| Pulumi Neo | Neo investigates live infrastructure, proposes IaC changes and previews resource changes. It has independent permission and approval modes, and can hand work through MCP. [Neo](https://www.pulumi.com/docs/ai/concepts/neo/), [permissions](https://www.pulumi.com/docs/ai/concepts/neo/permissions/) | Present a plan and expected resource changes before approval. Apply the same controls through every interface. | Read-only mode is scoped to Pulumi Cloud, so downstream credential access needs its own limits. Neo cannot initialize new Pulumi projects. [Getting started](https://www.pulumi.com/docs/ai/neo/get-started/) |
| Railway CLI and MCP | `railway up` uploads local source and follows deployment status. Detached mode returns after queuing. Railway exposes CLI and MCP integration, reuses CLI login, and distinguishes hosted and local MCP tool sets. [Source deployment](https://docs.railway.com/cli/up), [MCP](https://docs.railway.com/ai/mcp-server) | Build a complete source-to-release workflow and expose the same service through CLI and MCP. Report queued, deployed and healthy as different states. | MCP destructive-action annotations depend on client behavior. Lyara must enforce approvals on the server. |

## Five adaptations, in priority order

These are implementation recommendations for this repository, not claims that a vendor uses Lyara's exact mechanisms.

1. Make approval a persisted capability for an exact plan. Store the target app, operation list, redacted parameters, source archive hash and canonical plan digest. A local human approves that digest. Changing the plan invalidates approval. The shared service checks approval again immediately before each write, whether the caller is the web UI, CLI or MCP. AWS's scoped directed actions and Pulumi's separate controls support this design. Keep Liara credentials in the adapter and exclude them from the plan. See [AWS directed actions](https://docs.aws.amazon.com/devopsagent/latest/userguide/working-with-devops-agent-working-with-directed-actions.html) and [Pulumi permission boundaries](https://www.pulumi.com/docs/ai/concepts/neo/permissions/).

2. Finish the source-deployment transaction. Inspect manifests as data, show the selected platform and explicit plan ID, create an immutable filtered archive, upload it, create a release and retain its exact ID. Poll that release to a terminal state before dependent configuration steps. Then check the public health URL independently. A queued release, a completed release and a healthy application require different messages. Railway's documented detached behavior illustrates why submission success cannot prove deployment success. HolmesGPT's verification checks also consider logs and resource signals after rollout. See [Railway source deployment](https://docs.railway.com/cli/up) and [HolmesGPT verification](https://holmesgpt.dev/latest/operator/deployment-verification/).

3. Require evidence for diagnosis. Save redacted observations with source, time window, retrieval time, unit and an evidence ID. A hypothesis cites the IDs that support or contradict it. Missing metrics, denied log access and failed queries stay visible. A high-memory observation can support resource pressure; a recent deployment can support a regression hypothesis. Neither alone proves causality. Return `inconclusive` when the observations cannot distinguish the causes. incident.io's revisable findings and Rootly's outcome taxonomy provide practical examples. See [incident.io's finding records](https://incident.io/blog/building-investigations-what-it-takes-to-build-an-ai-sre) and [Rootly result interpretation](https://docs.rootly.com/ai/ai-sre/reading-the-result).

4. Keep execution durable and recovery explicit. Persist a small action journal beside graph checkpoints. Record planned, started, succeeded, failed and unknown outcomes with the remote resource or release ID. A restart resumes observation of an existing operation instead of blindly repeating its mutation. Treat a timeout after sending a write as unknown until a read reconciles it. Poll with a deadline and stop dependent actions on failure. Keep a known uploaded source ID so recovery can propose redeployment through the documented API. This is a local reliability recommendation. The inspected product docs do not establish a general exactly-once guarantee. AWS's own integration example uses bounded polling, terminal failure handling and duplicate-dispatch protection. [AWS lifecycle workflow](https://aws.amazon.com/blogs/devops/automate-planned-lifecycle-upgrades-with-aws-devops-agent-and-kiro/)

5. Reuse one planner contract and one tool service. API, Codex CLI and Claude Code should return the same validated plan structure. None receives a path for arbitrary API calls or shell execution against production. MCP tools call the same inspect, observe, propose and status methods as the UI. Keep human approval outside model-controlled tool arguments. kagent documents provider and backend differences; Railway demonstrates integration with several external clients. This supports interchangeability while keeping authority in Lyara's own code. See [kagent provider configuration](https://kagent.dev/docs/kagent/1.x/setup/model-providers/about-model-providers/), [kagent approval behavior](https://kagent.dev/docs/kagent/1.x/agents/human-in-the-loop/) and [Railway MCP](https://docs.railway.com/ai/mcp-server).

## Adaptations now implemented

These are Lyara implementations inspired by the researched patterns, not vendor
feature parity. AWS directed actions, Rootly result interpretation and Railway
up primary references were checked again on 2026-10-23.

| Research pattern | Implemented in Lyara | Boundary |
| --- | --- | --- |
| AWS / Pulumi: change preview and controlled recovery | Per-action impact/risk/recovery; exact displayed digest; source recovery with fresh approval | No automatic data/env/DNS rollback or invented cost |
| Rootly / incident.io: evidence-backed outcomes | Before/after evidence report, timestamps, source IDs, approval and action journal | Website health is distinct from evidence that an operation took effect |
| Railway / HolmesGPT: queued, deployed and healthy are distinct | Pending release IDs persist and exact-release reconciliation is read-only | No duplicate writes or silent execution of remaining steps |
| Conversational follow-up | Preserve original target/request, parent/child links, re-inspection and fresh approval | Structural answer changes limited to port/platform/plan ID |
| kagent / Railway: interchangeable providers and clients | One schema and service for API/Codex/Claude and UI/CLI/MCP | No model-controlled approval tool |

Next candidates are ranked hypotheses with supporting/contradicting evidence IDs,
passive monitoring history, and a plan selector backed by a verified current
Liara catalog. Autonomous writes and multiple runtime agents are not prerequisites.

## What to demonstrate now

Use the production workflow with a clearly labeled mock transport for an offline demo. Show a source inspection and deployment proposal, pause for approval, resume after a process restart, display the release status, and verify HTTP health. In a second run, inject a failed release or ambiguous write response and show that dependent operations stop without duplicate execution. For diagnosis, show an HTTP 500 example with cited log evidence and another with insufficient telemetry. These scenarios check the proposed design; they do not prove a live Liara integration.

## Gaps and uncertainties

- No live account was used to test these eight products. This comparison verifies public descriptions and design patterns, not reliability, accuracy, regional availability, latency or price. No performance ranking is justified.
- AWS's earlier engineering post says the agent only generates mitigation plans. Current directed-action documentation describes approved execution. Prefer the explicit current feature documentation, and avoid repeating the older restriction as a current universal rule. [Earlier explanation](https://aws.amazon.com/blogs/devops/how-aws-devops-agent-uses-multi-agent-reasoning-to-find-root-causes/), [directed actions](https://docs.aws.amazon.com/devopsagent/latest/userguide/working-with-devops-agent-working-with-directed-actions.html)
- Rootly's product page says changes wait for a person. Its technical documentation warns that selected MCP, provider and private-agent tools can mutate state without confirmation. Approval must therefore be tested at the actual tool boundary. [Product page](https://rootly.com/agents), [technical warning](https://docs.rootly.com/ai/ai-sre/overview#frequently-asked-questions)
- MCP exposes tools; it does not itself prove safe execution or human authorization. Railway says destructive annotations prompt only in clients that respect them. kagent's approval coverage depends on the execution backend and tool binding. [Railway security considerations](https://docs.railway.com/ai/mcp-server#security-considerations), [kagent approvals](https://kagent.dev/docs/kagent/1.x/agents/human-in-the-loop/)
- Model portability needs capability checks, not only a configurable base URL. HolmesGPT labels local Ollama support experimental and warns about inconsistent tool calling. [Ollama support](https://holmesgpt.dev/0.43.0/ai-providers/ollama/)
- Liara-specific authentication, payload shapes, metric units, source upload responses, release states and recovery behavior still require live validation against the documented API and an approved account. A product working on AWS, Azure or Kubernetes proves none of these details.
- Leave service topology graphs, autonomous write policies, incident memory retrieval and multiple coordinating agents until real operations show a need. The MVP can implement the useful safety and evidence patterns with one workflow, typed tool methods and SQLite.
